# CuteBot Code Club — 6-Session Programme Plan

## Overview

A six-session introduction to programming and robotics using the micro:bit and ELECFREAKS Cutebot.

**Audience:** year 5-6
**Session length:** 30 minutes
**Number of sessions:** 6
**Experience:** Mixed ability and variable attendance

The programme is designed around the Raspberry Pi Code Club approach of:

* **Explore** — Try things out and discover what happens
* **Design** — Plan and build a solution
* **Invent** — Extend, experiment and make it your own
* **Think** — Predict, debug, explain and reflect

The aim is not simply to teach children how to use a Cutebot. Each session introduces a **fundamental programming concept** through a practical robotics problem.

---

# Programme Goals

By the end of the programme, children should have encountered and practised:

* Sequence
* Events
* Loops
* Conditions
* Inputs and outputs
* Sensors
* Variables
* Algorithms
* Testing and debugging
* Decomposition
* Optimisation
* Explaining and evaluating code

Children should also become comfortable with the idea that programming is an iterative process:

> **Try → Test → Notice → Change → Test again**

# Session 1 — 🚗 Wake Up Your Cutebot

## Core concept

**Sequence and parameters**

Computers follow instructions in the order they are given. Small changes to parameters can change the robot's behaviour. A parameter is a value you give a command to tell it exactly what you want it to do.

## Hardware

* Cutebot
* micro:bit

## Explore

Experiment with:

* Forward
* Backwards
* Left
* Right
* Stop
* Speed
* Duration

Questions:

* What happens if you change the speed?
* What happens if you change the duration?
* How far does the robot travel?

## Design

### Straight Line Challenge

Make Cutebot travel from a start line to a finish line and stop.

Encourage children to experiment with:

* Speed
* Time
* Different movement sequences

## Invent

### Robot Dance

Create a short robot dance using movement.

Optional additions:

* LEDs
* Sounds
* Spins
* Pauses

## Think

Give children a prediction problem:

> The robot is supposed to travel 50cm but travels 70cm. What could you change?

Introduce the idea of **testing and debugging**.

## Extension

### Figure of 8 Challenge

Can Cutebot drive in a figure of 8?

Encourage experimentation with:

* Turn duration
* Motor speed
* Different speeds for each motor

### Optional advanced extension

Introduce the line-tracking sensors and allow confident children to experiment with line following.

# Session 2 — 🧭 Robot Navigator

## Core concept

**Loops and algorithms**

Repeated instructions do not always need to be written repeatedly.

## Hardware

* Cutebot motors

## Explore

Start with repetitive instructions:

```text
Forward
Forward
Forward
Forward
Forward
```

Ask:

> Can we make this shorter?

Introduce a repeat loop.

Compare:

```text
Forward
Forward
Forward
Forward
Forward
```

with:

```text
Repeat 5 times
    Forward
```

## Design

### Navigate the Grid

Create a simple floor grid.

Children need to program Cutebot to travel from START to FINISH.

Possible routes should include:

* Straight sections
* Turns
* A longer route
* A shorter route

## Invent

### Robot Dance-Off

Create a more complicated dance using:

* Loops
* Movement
* LEDs
* Sounds

Challenge:

> Can you create a dance using fewer blocks?

## Think

Show two programs that produce the same result.

Ask:

* Which is easier to understand?
* Which is easier to change?
* Which uses fewer instructions?

Introduce the idea that **good code is not just code that works**.

# Session 3 — 🛑 Don't Crash!

## Core concept

**Conditions and sensors**

The robot can use information from the world to make decisions.

## Hardware

* Ultrasonic distance sensor
* Cutebot motors

## Explore

Experiment with the ultrasonic sensor.

Ask:

* What happens when an object is close?
* What happens when it is far away?
* What number does the sensor give you?

## Design

### Don't Crash

Program Cutebot to:

1. Drive forwards
2. Check the distance
3. Stop when an obstacle is close

Introduce:

```text
IF
```

and explain that programs can make decisions.

## Invent

### Obstacle Course

Create an obstacle course.

Children can choose what Cutebot should do when it detects an obstacle:

* Stop
* Reverse
* Turn left
* Turn right
* Spin

Different solutions should be encouraged.

## Think

Introduce:

**INPUT → DECISION → OUTPUT**

For example:

```text
Distance sensor
       ↓
Is the object closer than 10cm?
       ↓
      YES
       ↓
      TURN
```

Questions:

* How does your robot know what to do?
* What happens if you change the distance?
* What happens if the robot is moving too quickly?

---

# Session 4 — 🛣️ Stay on Track

## Core concept

**Iteration and sensor-based decisions**

The robot needs to repeatedly check its surroundings and adjust its behaviour.

## Hardware

* Line-tracking sensors
* Cutebot motors

## Explore

Introduce the line sensors.

Children experiment with:

* Black
* White
* Left sensor
* Right sensor

Ask:

> What does each sensor see?

## Design

### Follow the Line

Create a simple black-line track.

Children program Cutebot to follow it.

The key idea is:

```text
Check sensor
↓
Make a decision
↓
Move
↓
Check again
↓
Make another decision
```

## Invent

### Design a Track

Children create their own line-following course.

Suggested rules:

* Must contain a straight section
* Must contain at least one corner
* Must have a start and finish
* Should be possible for another robot to attempt

Swap tracks between groups.

## Think

Investigate why robots wobble or leave the track.

Questions:

* What happens if the robot goes faster?
* What happens if it goes slower?
* What happens if the motors have different speeds?
* Why does the robot need to check the sensors repeatedly?

Introduce the idea of **feedback**.

# Session 5 — 🚑 Robot Rescue

## Core concept

**Combining concepts and using variables**

Children now use several programming concepts together to solve a larger problem.

## Story

A robot has been sent into a dangerous area to rescue a stranded explorer.

It must navigate the area, avoid obstacles and signal when the rescue is complete.

## Explore

Break the problem into smaller problems.

Can you:

* Move the robot?
* Detect an obstacle?
* Turn?
* Follow a line?
* Flash an LED?
* Stop at the rescue zone?

## Design

### Rescue Mission

Create a course with:

* Start zone
* Route
* Obstacle
* Rescue zone
* Finish zone

Children plan their algorithm before coding.

Example:

```text
START
  ↓
Follow route
  ↓
Obstacle?
  ├── YES → Avoid obstacle
  └── NO → Continue
  ↓
Rescue zone?
  ↓
Stop
  ↓
Signal rescue
```

## Invent

Allow children to customise their rescue robot.

Ideas:

* Alarm
* Flashing lights
* Different responses to obstacles
* Rescue music
* Countdown
* Time challenge

## Think

### Variables

Introduce a variable where useful.

For example:

```text
distance = sensor reading
```

Then:

```text
IF distance < 10
    avoid obstacle
```

Explain that a variable can give information a name so that the program can use it.

## Reflection

Ask:

> What part of your robot was hardest to get working?

> What did you change to fix it?

> What would you improve next?

# Session 6 — 🏆 CuteBot Grand Challenge

## Core concept

**Algorithms, decomposition, debugging and optimisation**

The final session is deliberately open-ended.

Children should have to decide how to solve the problem rather than being given step-by-step instructions.

## Challenge

### Autonomous Delivery Robot

Cutebot has been hired as a delivery robot.

It must:

1. Start at the depot
2. Navigate the course
3. Avoid obstacles
4. Reach the delivery zone
5. Signal that the delivery is complete

The exact course can be changed between clubs.

## Explore

Allow time to:

* Test the course
* Test sensors
* Test movement
* Identify difficult sections

## Design

Children should plan their solution before coding.

They can use:

* Drawings
* Flowcharts
* Pseudocode
* Notes

Example:

```text
START
 ↓
Drive forward
 ↓
Follow line
 ↓
Obstacle?
 ├── YES → Turn
 └── NO → Continue
 ↓
Delivery zone?
 ├── NO → Continue
 └── YES → Stop
             ↓
          Flash LEDs
```

## Invent

Children can add their own features.

Possible ideas:

* Different delivery signals
* Faster route
* Obstacle strategy
* Sound effects
* LED patterns
* Automatic start
* Timer

## Think

### Debugging Challenge

Ask children to identify and fix problems in their programs.

Reflection questions:

* What didn't work?
* How did you find the problem?
* What did you change?
* Did your change solve the problem?
* Could your code be simpler?
* Could your robot be faster or more reliable?

# Differentiation

The programme should support children with different levels of experience without requiring separate lesson plans.

## Explore

Everyone should be able to participate.

Give children a working starting point and encourage experimentation.

## Design

Provide a clear goal but allow children to choose their own solution.

## Invent

Provide optional challenges for children who finish early.

These should encourage:

* Experimentation
* Creativity
* Optimisation
* Combining concepts

rather than simply adding more code.

## Think

Use questions that can be answered at different levels.

For example:

> Why did the robot turn?

A beginner might answer:

> Because the sensor detected something.

A more experienced child might explain:

> The distance sensor provided an input, the `if` statement compared it with a threshold and the program changed the motor output.

Both answers demonstrate learning.

---

# Suggested Challenge Levels

Avoid requiring every child to complete Bronze, Silver and Gold.

Instead, use difficulty as an optional progression.

### 🟢 Starter

A highly scaffolded challenge that most children should be able to complete.

### 🔵 Challenge

Requires children to modify or combine concepts.

### 🟣 Invent

An open-ended problem with multiple possible solutions.

### 🧠 Think

A prediction, debugging, optimisation or explanation activity.

# Session Format

Each 30-minute session should roughly follow:

|      Time | Activity              |
| --------: | --------------------- |
|   0–5 min | Introduce the mission |
|  5–10 min | Explore               |
| 10–20 min | Design                |
| 20–27 min | Invent / challenge    |
| 27–30 min | Think / share         |

This should remain flexible. If children are deeply engaged in experimenting, allow the Explore or Design phase to run longer.

---

# Volunteer Approach

Volunteers should avoid immediately giving children the code.

Instead, use questions such as:

### When something doesn't work

> What did you expect to happen?

> What actually happened?

> Which part of the program controls that?

> What could you change?

### When a child is stuck

> What is the smallest part of the problem we could solve first?

> Can you make the robot do just that?

### When a child finishes quickly

> Can you make it work differently?

> Can you make it more reliable?

> Can you make the code shorter?

> Can you design a challenge for someone else?

---

# Key Principle

The objective is **not** for every child to finish the same amount of code.

The objective is for every child to:

1. Make something
2. Experiment with it
3. Encounter a problem
4. Try to solve the problem
5. Understand something they didn't understand before

> **Programming is not about getting the right answer first time. It is about learning how to make things work.**

# Future Extensions

If the programme is successful, future missions could introduce:

* Radio-controlled Cutebots
* Multiple robots
* Robot football
* Light sensors
* Sound
* Functions
* More advanced variables
* Scoring systems
* Timed races
* Cooperative challenges
* Designing and building a robot course
* Student-created missions

The six-session programme should therefore provide a foundation that can be extended without having to introduce every Cutebot feature immediately.
